Portfolio Stack Picks

One site with two jobs. Visitors see your frontend craft. The repo and the running system prove you can build, ship and run it yourself. This page picks the tools for that, so we can agree before writing the plan.

The short version

Frontend
React + TypeScript + Vite, the same stack as A-Store. GSAP for the scroll effects. Admin is a separate small app.
Backend
A separate Node.js + Fastify API with PostgreSQL. The frontend never touches the database.
Platform
AWS only. k3s Kubernetes on one EC2 t4g.small spot server (2 vCPU, 2 GB), inside a VPC you build. First by hand, then with Terraform.
Delivery
GitHub Actions tests, builds and scans images. Flux deploys them from git. It is lighter than Argo CD, which matters on 2 GB.
Cost
About $11 a month, paid from AWS sign-up credits for about a year. A domain is extra, about $12–16 a year.
Your part
You do every Docker, Kubernetes, AWS, networking and CI step by hand. I write the app code, write a guide for each step, and check your work.

What recruiters and hiring managers will see

The 30-second look · recruiter

  • A fast, polished page on your own domain, with HTTPS.
  • Their own name in the greeting when they open their personal link.
  • A small "How this site runs" section: Kubernetes on AWS, shipped by a pipeline you built.
  • Contact options that work on a phone in one tap.

The 10-minute look · engineer

  • A README with the architecture diagram and a "rebuild from zero" section.
  • A green CI badge. The Actions tab shows tests, a security scan and builds on every push.
  • An infra/ folder: Terraform for AWS, a Helm chart for the app.
  • Short decision notes: what you picked, what you turned down, and why.
  • Runbooks for restoring the database and rolling back a release, each tested once and dated.

An example CV line

Built and run my portfolio on AWS: Terraform-built VPC and EC2, single-node k3s Kubernetes on spot, Helm and Flux (GitOps), GitHub Actions CI with image scanning, a Node.js API with PostgreSQL and automated S3 backups.

Say it plainly. This is one server, so it has no high availability, and it is not "production Kubernetes at scale". Write down that limit and what you would change for more traffic. Engineers trust a candidate who states the trade-offs. The EKS weekend lab below lets you talk about managed clusters from real experience.

How the credits work

  • New AWS accounts get $100 at sign-up, plus up to $100 more for five small setup tasks. One of them is setting an AWS Budget.
  • Upgrade to the paid plan before the free plan's 6 months end, or the account is suspended.
  • Credits stay usable for 12 months from sign-up, so they pay for about a year of this setup.
  • Check which charges the credits don't cover. Domain registration is likely not covered.
  • When the credits run out, keep paying about $11 a month, or shut it down and rebuild it with one command from Terraform and Helm for interview demos.

2 GB of memory is tight, which is why Flux replaces Argo CD. AWS can take a spot server back at short notice. A one-instance Auto Scaling group starts a replacement and reattaches the data disk (EBS), so the database survives. Setting that up is a lesson in itself.

How the learning works

Each stage ends with something that works on its own. Dashed stages are optional.

  1. App on your Mac (Compose)
  2. Kubernetes on your Mac (k3d)
  3. AWS by hand
  4. Same AWS in Terraform
  5. Live on your domain
  6. CI pipeline
  7. CD with Flux
  8. Backups and monitoring
  9. EKS weekend lab

I do

  • Write all the app code: site, admin, API, database schema, tests.
  • Write a guide for each stage.
  • Review everything you write and every output you paste, then point out what to fix.

You do

  • Dockerfiles, Compose, Kubernetes YAML, the Helm chart.
  • AWS console work, then the same in Terraform.
  • DNS, HTTPS, firewall rules, the GitHub Actions workflows, Flux.
  • Run the check commands and paste the output to me.

What each stage guide contains

  • What you're building and why, in plain words, with a diagram.
  • Your steps, in order.
  • Check commands and the output you should see.
  • What to paste to me for review.
  • Common mistakes at this stage.
  • Interview questions you can answer once it's done.

What the site and admin do in v1

Public page · one scroll

  • Welcome: a placeholder until it gets its own design session.
  • About: your path as a timeline, frontend → backend → DevOps → frontend.
  • Tech stack, grouped, with an honest level for each.
  • Projects: A-Store before and after, with live links and real numbers.
  • How this site runs: a simple version of the diagram above. New.
  • Contact. Phone and WhatsApp can be shown to invited visitors only.

You choose the look from mockups in a later session.

Admin

  • Sign in with a password plus a 6-digit code from an authenticator app.
  • Site content: edit your profile, section text, projects and contact details, and choose what the public page shows.
  • Invites: one link per person, with name, company, role and greeting. Choose what that person sees. Copy, block or delete the link.
  • Visits: when each link was opened, on what device, which sections were read, for how long, and what was clicked.

Later: printable QR cards, a résumé PDF stamped per invite, an email alert on first open, a log of link previews, city-level location.

Kept from the original spec: the invite code format, counting a visit only when the page's script runs (so link previews never count), the privacy note, data that deletes itself, and the scroll-effects cookbook.
