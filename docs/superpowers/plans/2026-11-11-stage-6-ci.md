# Stage 6: CI (GitHub Actions + OIDC to AWS)

> Guide-and-review stage. The owner writes the workflows and the Terraform from starter files. Claude writes the starters, the guide and the review. Claude runs no git commands. Steps use checkboxes.

**Goal:** Every push runs lint, typecheck and tests. Pushes to `main` also build arm64 images for site, admin and api with a layer cache, scan them with Trivy and push them to GHCR. Pull requests that touch `infra/` get a `terraform plan` through GitHub OIDC, with no stored AWS keys.

**Spec:** `docs/superpowers/specs/2026-11-11-portfolio-design.md`: §4 rows CI, Registry and CI to AWS; §5 Security basics (credentials, IAM scope); §7; §8 stage 6; §11 (Trivy thresholds and caching are the builder's call).

**Depends on:** Plans 1–5 (the `pnpm test`, `typecheck`, `lint` and `build` scripts, plus the owner's three Dockerfiles), stage 4 (Terraform state bucket, backup bucket, Route 53 zone) and stage 5 (the live domain). The repo is public on GitHub.

## Reconsider before executing

- **Terraform plan needs more than the spec's IAM scope.** The spec scopes the CI role to the state bucket, the backup bucket and Route 53 records. A `plan` also refreshes the VPC, ASG, EBS, EIP and IAM resources, which needs read-only `Describe*`/`Get*`/`List*` on them. Proposal: add a read-only policy limited to those services, and still no write access outside the three resources. This is a spec deviation, so the owner decides.
- **arm64 runners:** check that GitHub's native `ubuntu-24.04-arm` runners are still free for public repos. If they are, use them. If not, fall back to QEMU through `docker/setup-qemu-action`, which is slower and less like the real server.
- **Pin every third-party action to a full commit SHA**, not a tag. Trivy's action has had tag-hijack incidents. At execution time, check the current versions of `aquasecurity/trivy-action`, `docker/build-push-action`, `aws-actions/configure-aws-credentials` and `pnpm/action-setup`.
- **Trivy threshold:** fail on `HIGH,CRITICAL` with `ignore-unfixed: true`, so CI blocks only when a fix exists. A `.trivyignore` needs a reason line on every entry.
- **Cache:** `type=gha` buildx cache, one scope per image. The repo cache limit is 10 GB. Check whether eviction becomes a problem.
- **Image names:** `ghcr.io/<owner>/pf-site`, `pf-admin` and `pf-api`, tagged `sha-<short>`, and only `main` builds push. Stage 7's tag bump reads these exact names, so confirm they match what Plan 5 and stage 2 used.
- **Cost:** $0. Actions minutes are free for public repos, and the OIDC role adds no AWS charge.

## Steps

- [ ] **Step 1 (Claude):** Write the three starter files with the four-part explanation (§7: summary, why, line by line, what to learn plus 3–5 interview questions, his part plus a check command). Publish the guide artifact and write `docs/learn/06-ci.md`.
- [ ] **Step 2 (owner):** Finish `ci.yml` on a branch and push.
  - Check: `gh run list --limit 1` shows `completed success`.
  - Check: `gh run view --log | grep -c "pnpm test"` is ≥ 1.
- [ ] **Step 3 (owner):** Prove the gate works. Push a branch with a failing test.
  - Check: the run is red and the image jobs don't start.
  - Revert it.
- [ ] **Step 4 (owner):** Merge to main.
  - Check: `docker manifest inspect ghcr.io/<owner>/pf-api:sha-<short> | grep architecture` prints `"arm64"`.
  - Check: the package page shows Public.
- [ ] **Step 5 (owner):** Prove the cache works. Re-run the workflow with no changes.
  - Check: the build step logs show `CACHED` for the dependency layers, and the image jobs run at least 50% faster than the first run (note both times).
- [ ] **Step 6 (owner):** Prove Trivy works. On a branch, temporarily pin a base image tag known to have a fixed HIGH CVE.
  - Check: the Trivy step fails with `exit code 1` and lists the CVE.
  - Revert it.
- [ ] **Step 7 (owner):** Run `terraform apply` for `infra/github-oidc.tf`, then open a PR that changes a tag in `infra/`.
  - Check: the plan job log shows `aws sts get-caller-identity` with an `assumed-role/<ci-role>/...` ARN, and `Plan: 0 to add, 1 to change, 0 to destroy`.
- [ ] **Step 8 (owner):** Prove the trust scope. Run the plan workflow from a `push` event (temporarily) or a fork.
  - Check: `Not authorized to perform sts:AssumeRoleWithWebIdentity`.
- [ ] **Step 9: Review gate.** The owner pastes both workflow files, the `.tf` file and the outputs from Steps 2–8. Claude reviews them and explains every fix. Stage 7 starts only after that.

## Guide artifact outline (§7)

- **What and why:** CI as the gate. Why images are built only on main. Why OIDC beats access keys (short-lived tokens, nothing to leak).
- **Diagram:** push → jobs (check → build matrix → Trivy → GHCR) and PR → OIDC token → STS → role → S3 state and plan.
- **Steps:** Steps 2–8 above.
- **Check commands:** as listed in the steps.
- **What to paste for review:** both workflows, `github-oidc.tf`, and the logs from Steps 2–8.
- **Common mistakes:**
  - `id-token: write` missing
  - `sub` claim too broad (`repo:x/*`)
  - building amd64 by default
  - cache scope shared across images, so they evict each other
  - Trivy scanning after the push instead of before
  - pnpm store cache keyed on the wrong lockfile path
- **Interview questions:**
  - How does GitHub OIDC federation work, and what does the `sub` claim protect?
  - Why pin actions by SHA?
  - Cache-from vs cache-to, and `mode=max`?
  - Why `ignore-unfixed`?
  - How would you speed up a slow monorepo pipeline?
